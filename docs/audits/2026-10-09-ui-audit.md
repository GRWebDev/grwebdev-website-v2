# GRWebDev technical UI audit

Audit date: October 9, 2026. Scope: the working tree at the time of the audit and a fresh production build.

This is a historical snapshot taken before the hero, overlay, and enlarged-text fixes in this stack. Source links point to the audited commit.

## Anti-pattern verdict

Pass. The implementation has a distinct community identity: real community photography, event flyers, sponsor marks, square geometry, and a consistent black/red palette. No gradient text, decorative card grids, excessive rounding, glass panels, repeated eyebrow labels, or hidden reveal content appeared in the reviewed code.

The bundled detector flagged Open Sans as overused and outside DESIGN.md. Those are false positives for this project: DESIGN.md explicitly commits to Open Sans Variable. Preserve the established typeface. Its white-color advisory is valid token drift, recorded below, rather than a visual design failure.

## Executive summary

Six findings: **0 P0, 3 P1, 2 P2, 1 P3**. The release priorities are preserving access to events across screen sizes, providing text equivalents for flyer logistics, and keeping navigation available with enlarged text. The site fits ordinary mobile, tablet, and desktop layouts well. Most accessibility and performance foundations are already present.

No application source was changed. This report and its screenshots are the audit deliverables.

## Verification and limits

- `npm run build` passed and generated 16 pages. The asset-pruning integration removed 13.94 MiB of unreferenced raster files.
- Inspected source for every page template, shared layout, navigation, footer, styles, event selection, and showcase invitation/dialog.
- Inspected seven representative routes at 320, 390, 768, 1280, and 1920 CSS pixels: home, about, board, board member, sponsors, sponsor detail, and 404. No horizontal overflow or completed broken image loads appeared in those 35 ordinary-layout checks. Each had one h1.
- Opened the native mobile menu and checked reverse keyboard navigation through board links. Focus outlines and underlines were visible.
- Used temporary, ignored build fixtures with script tags removed to check progressive fallback. Added `html { font-size: 200% }` to one fixture to simulate enlarged default text. This is a font-enlargement check, not browser zoom emulation.
- Calculated contrast for the shared opaque palette after converting OKLCH to sRGB: body ink against white is about 18.58:1; red against white is about 7.14:1. These calculations do not certify every photograph, flyer pixel, focus state, or third-party widget state.
- The in-app browser was used for visual and DOM checks. The Playwright suite was not run because its configured Chromium executable is missing. The audit does not claim a fresh verification of the cookie-enabled first-visit dialog, donation checkout, external forms, screen-reader behavior, or browser compatibility across engines.
- The detector scan's warnings were reviewed against PRODUCT.md and DESIGN.md rather than accepted automatically.

## Detailed findings

### [P1] Narrow layouts remove event destinations

Location: [EventGrid.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/EventGrid.astro#L81).

Category: Responsive design / Accessibility.

At 320, 390, and 768 pixels, only October 9, October 15, and October 23 remain visible. At 1280 pixels, the October 26 presentation and November 13 meetup also appear. At 1920 pixels, all eight selected entries appear. The `nth-child` rules remove links with `display: none`; there is no event-specific expansion control or equivalent full listing on the homepage.

Impact: Mobile visitors miss the October 26 presentation entirely when scanning Events. Enlarging a desktop layout until it becomes narrow also reduces access to information.

Standard: [WCAG 1.4.10, Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html), which requires preserving information and functionality as content reflows.

Recommendation: Keep the same upcoming-event set accessible at every width. Change the column count rather than the content count, or provide an explicit control that reveals the remaining events. Keep past events separate from upcoming events if preserving the current mixed selection.

Suggested command: `$impeccable adapt EventGrid`.

### [P1] Flyer logistics lack equivalent text

Location: [EventGrid.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/EventGrid.astro#L115) and the event schema in [content.config.ts](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/content.config.ts#L46).

Category: Accessibility.

The October 9 flyer says 8:00 AM and identifies an online event. The October 15 flyer names The Factory and displays 8:00 AM and a street address. The accessible link names provide the title, date, and Meetup destination; the image alt text provides only the event title. The schema contains no structured start time or venue for rendering equivalent logistics.

Impact: Visitors who cannot read the images must open Meetup to discover basic details that sighted visitors receive on this page. Flyer text also stays small and rasterized when users enlarge default text.

Standard: [WCAG 1.1.1, Non-text Content](https://www.w3.org/WAI/WCAG22/Understanding/non-text-content.html). Flyer-based event details also warrant review against [WCAG 1.4.5, Images of Text](https://www.w3.org/WAI/WCAG22/Understanding/images-of-text.html).

Recommendation: Add structured time, time zone, venue, and online/in-person fields. Render the essential information as HTML next to each flyer. Give links an accessible name derived from that text; keep the flyer as a community artifact without relying on it to convey logistics.

Suggested command: `$impeccable harden EventGrid`.

Evidence: [event flyer screenshot](assets/2026-10-09-event-flyers.png).

### [P1] Enlarged text pushes fallback navigation outside the viewport

Location: [nav.css](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/styles/nav.css#L49), particularly the nonwrapping flex bar, rem-sized logo, donation fallback, and rem-sized menu control.

Category: Responsive design / Accessibility.

At 320 pixels with a doubled root font size and scripts removed, document width grows to 547 pixels. The donation link spans x=198 to x=443, and the navigation menu spans x=459 to x=547. Main content stays within the viewport. At normal text size, the fallback fits.

Impact: Visitors using enlarged default text must scroll sideways to reach navigation. The problem occurs in the usable fallback when the donation widget is blocked, unavailable, or still loading.

Standard: [WCAG 1.4.4, Resize Text](https://www.w3.org/WAI/WCAG22/Understanding/resize-text.html) and [WCAG 1.4.10, Reflow](https://www.w3.org/WAI/WCAG22/Understanding/reflow.html). The measured failure is the enlarged-text fallback, not a claim that the hydrated widget fails the same way.

Recommendation: Allow the header to wrap or use a compact layout when its contents no longer fit. Keep the menu inside the viewport, let the donation link take another row, and constrain logo growth without shrinking the menu's usable target. Verify both fallback and loaded widget at enlarged text sizes.

Suggested command: `$impeccable adapt Header`.

Evidence: [enlarged header screenshot](assets/2026-10-09-header-enlarged-text.png).

### [P2] Mobile receives a desktop-sized hero asset

Location: [Home.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/Home.astro#L5).

Category: Performance.

The hero is generated once at 2000 pixels wide and weighs 276,914 bytes, about 270 KiB. Every viewport references that same CSS background. It has no responsive source selection.

Impact: Narrow screens download the full desktop image. This is the largest first-party asset in the build and adds avoidable transfer on slower connections. No measured LCP regression is claimed.

Standard: Responsive image delivery; no direct WCAG violation established.

Recommendation: Generate a small set of suitable image widths and select them with media queries, or render a decorative responsive picture/image behind the hero copy. Preserve the existing photograph and contrast overlay. Compare transfer size and mobile LCP after the change.

Suggested command: `$impeccable optimize Home`.

### [P2] Time-sensitive content depends on an unrelated deployment

Location: [ShowcaseCampaign.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/ShowcaseCampaign.astro#L5), [EventGrid.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/EventGrid.astro#L16), and [deploy.yml](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/.github/workflows/deploy.yml#L3).

Category: Responsive/content behavior.

The submission deadline and upcoming-event selection are evaluated only at build time. The deployment workflow runs on pushes to main or manual dispatch and has no scheduled refresh. The campaign's comment acknowledges this behavior.

Impact: Without another deployment, the November 13 invitation can remain after submissions close, and the event selection remains frozen as dates pass. This is a maintenance dependency, not a claim that today's live content is already expired.

Standard: Product requirement to make the next event and next step clear; no direct WCAG violation established.

Recommendation: Add a scheduled rebuild and a deployment at campaign expiry, or make expiry a progressive client enhancement while maintaining fresh static fallback HTML. Document who owns the refresh schedule.

Suggested command: `$impeccable harden ShowcaseCampaign and EventGrid`.

### [P3] Overlay colors bypass the shared palette

Location: [Home.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/Home.astro#L15), its `#fff` text at line 32, and [ShowcaseDialog.astro](https://github.com/GRWebDev/grwebdev-website-v2/blob/edf674b/src/components/ShowcaseDialog.astro#L85).

Category: Theming.

The hero text hard-codes white, and the hero and dialog overlays hard-code black with opacity. Most other UI uses the shared tokens. White currently equals the tertiary token, so there is no present contrast defect from this exception.

Impact: A future palette adjustment would leave these elements behind, making theme maintenance less predictable.

Standard: DESIGN.md palette consistency; no WCAG violation established.

Recommendation: Use the existing white token and named overlay tokens, or explicitly document these intentional image-overlay exceptions. Preserve their verified opacity rather than mechanically replacing colors with a weaker overlay.

Suggested command: `$impeccable polish Home and ShowcaseDialog`.

## Patterns and systemic gaps

- Event discovery relies on raster flyers instead of structured logistics. This couples readable content, accessibility, and event updates to image production.
- The event grid treats content removal as a responsive layout tool. The number of columns should change independently of access to upcoming events.
- Header testing needs the fallback and enlarged-text combinations in addition to the successful hydrated mobile state.
- Static date checks need an operational refresh policy. Correct time-zone comparisons do not refresh already-published HTML.

## Positive findings

- A skip link, main landmark, language attribute, clear heading structure, labeled navigation, and current-page indicators are present.
- Native details navigation works without JavaScript. Its ordinary mobile layout opens within the viewport.
- Board and sponsor links have explicit names. Empty thumbnail alt text correctly avoids repeating their adjacent names.
- Images use generated WebP variants, explicit dimensions, lazy loading, and responsive sources. Maps are titled and lazy-loaded. The local dialog bundle is only 1,077 bytes before compression.
- Shared opaque text colors exceed AA contrast requirements. Reduced-motion behavior exists globally and for route transitions.
- The showcase has a static invitation and guards against missing dialog support or unavailable cookies. Existing browser tests cover these cases, though this audit did not rerun them.
- The established design system avoids the skill's major visual anti-patterns and keeps community artifacts visible.
